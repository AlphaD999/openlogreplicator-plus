==== code 60001: "incomplete row for table (obj: <number>), probably IOT, xid: <xid>, offset: <number>"

Occurs when a row cannot be reconstructed completely (common with IOTs or missing schema images).
Remediation: Ensure full schema mode or provide a schema snapshot; avoid schemaless mode for IOT tables.

A column value could not be decoded (often seen with LOB fragments or unexpected formats).
Remediation: Enable detailed logging (`unknown=1`) to capture raw bytes and provide schema for proper decoding.

==== code 60038: "couldn't find archive log for thread: <number> seq: <number>, found: <number>, thread is closed - waiting for delayed archival (instance recovery), sleeping <number> us"

On a RAC source, the archive of a closed (stopped) instance's thread is missing while later sequences exist.
The tail archive may still be produced by instance recovery on a surviving node; OpenLogReplicator keeps waiting instead of failing.
Remediation: Verify instance recovery/archival on the remaining nodes; if the archive never appears, restore it manually (report this issue if it persists).

==== code 60039: "RAC database detected - archives-only mode can not be disabled, the reader parameter \"archives-only\": false is ignored"

A RAC source database always runs in archives-only mode, because online redo logs of a RAC database reside in ASM and are not readable from outside the cluster.
An explicit `"archives-only": false` in the reader configuration therefore has no effect on a RAC database.
Remediation: Remove the parameter to silence the warning; only a non-RAC database can use online mode.

==== code 60041: "transaction <xid> takes over the undo slot of unfinished <xid> - the unfinished transaction is dropped"

An undo slot holds one active transaction at a time. When OpenLogReplicator sees a different transaction
take over a slot it had seen as still open, the previous transaction is assumed to have committed or
rolled back unobserved (which is expected when reading starts in the middle of the redo stream).
The unfinished transaction is discarded to let processing continue.
Remediation: Only reported with the `RECOVER_BROKEN_TRANSACTION` flag (`1 << 19`). Usually harmless;
if reported frequently, start reading from a position with no transactions in flight.

==== code 60042: "duplicate <owner>.<table> value for unique (<columns>), dropped: <columns>"

The unique key of a dictionary row is already indexed by a different row. This happens when the same
object is present in more than one container of a CDB, or when the same redo stream is processed twice.
Remediation: Only reported with the `ADAPTIVE_SCHEMA` flag (`1 << 2`), in which case the newly read row
wins and the previous holder is discarded. Without the flag the same condition is an error (50024).

==== code 60043: "memory pool exhausted with nothing left to swap for <seconds> s (allocated: <number> MB of <number> MB, free: <number> MB, blocked: <number> thread(s), open transactions: <number>, swappable: <number>) - modules: <modules> - replication is likely stalled; increase \"max-mb\", verify \"swap-path\" is writable, or skip the big transaction via \"transaction-max-mb\""

The memory pool is completely allocated, at least one thread is waiting for a chunk and the memory manager
has no transaction chunk left to swap out, so the parser (waiting for transaction memory) and the reader
(waiting for a read buffer) can no longer make progress. The message reports the pool state, how many
threads are blocked, how many transactions are open, how many of them are swappable and the per module
memory usage. Replication is stalled until the condition resolves.

Two independent limits can lead here:
* a single transaction bigger than the configured `max-mb` (or `swap-path` does not exist or is not writable -
  in that case transactions cannot be swapped out at all; `swap-path` is validated at startup since this
  release);
* the number of concurrently open transactions: every open transaction occupies at least
  `MEMORY_CHUNK_SIZE_MB` and only transactions with more than one chunk are swappable, so a workload with
  thousands of concurrent transactions can exhaust the pool even with small transactions. This case is
  reported with `swappable: 0`. Note that a fresh start positioned in the middle of an archive re-reads the
  whole archive from its beginning, so the peak number of open transactions can be the whole pre-start
  part of an archive.

Remediation: increase `memory.max-mb` (at least 110% of the biggest expected transaction and at least the
peak number of concurrently open transactions in MB plus the read/write buffers), make sure
`memory.swap-path` exists and is writable by the process user, or set `transaction-max-mb` to skip
transactions bigger than the configured size (their data is not replicated).

When the parser itself is blocked and nothing can be swapped out, the run is not recoverable (the commit
sorter is flushed only by the parser) and OpenLogReplicator terminates with error 10017 instead of waiting
forever.

==== code 60044: "file: <file name> - position: <number> - short read before the end of file (size: <number>), the file is not fully readable yet"

An archived redo log could not be read up to the position the reader expects to have:
either the read returned zero bytes although the file is larger than the current position, or the position
did not move at all for a longer time ("no progress at position: ..., size: ... for: ... s").

A filesystem bridge can report a size the file does not have yet - asmfs, for example, snapshots the size of
an ASM file when it is opened and answers later reads with zero bytes when the file was not fully visible at
that moment. The reader does not treat this as the end of the archive (that would silently skip the rest of
it and move the checkpoint past redo that was never read): it stops and the archive is read again on the next
pass, which is why the same warning can repeat.

Remediation: check the filesystem bridge (mount options, `arch-read-tries`/`arch-read-sleep-us` retry window),
or use a destination where the archive is written before it is read.
Repeated short reads are usually harmless for the data - they only delay replication.

==== code 60045: "redo thread: <number> has no archived redo log left to read (expected seq: <number>, highest known seq: <number>) - it stops holding back the low-water-mark (reason: no-work); its transactions can now be delivered after transactions with a higher SCN" / "redo thread: <number> did not advance for: <number> s - it stops holding back the low-water-mark (reason: timeout, \"idle-thread-release-us\"); ..."

Only reported with `idle-thread-release-us` set (`source` element, 0 = strict). A redo thread was left out of the
low-water-mark of the commit sorter, for one of two reasons - the field `reason:` says which:

`reason: no-work`:: The archive list reports nothing left to read for this thread: everything it still has to read
  (`expected seq`) is beyond the highest sequence the list returns (`highest known seq`), nothing of it is queued
  and nothing is parked. Waiting can not move its parsed position in that state, so the release is a statement
  about the data and not a guess about when the next archive might arrive - this is the normal, expected case for
  the threads of instances that archive rarely (measured: three of four RAC threads hold 0.4-0.9 GB/h against 72 GB/h
  of the fourth, so they are "empty" for minutes at a time).
`reason: timeout`:: The fallback. The thread did not report a new parsed SCN within `idle-thread-release-us`, i.e.
  the source does not tell what is left (a failing archive list query, a list that keeps returning nothing, an
  archive that can not be opened). A run that reports this regularly has a problem with the source, not with the
  release policy.

_IMPORTANT:_ the global SCN order is not guaranteed for the transactions of the released thread any more - if it
later delivers redo with an SCN below what has already been written, those transactions are written after
transactions with a higher SCN. With `reason: no-work` that only happens when an archive of the thread arrives
*after* the other threads have already delivered past its SCN range, which is exactly the case the timeout used to
wait for; a thread that comes back behind the water-mark does not hold it back until it has caught up (an
informational `has work again and is behind the low-water-mark` line follows). Set `idle-thread-release-us: 0` if
strict ordering by SCN is required - the price is that an instance which is quiet for a long time holds back every
transaction of the others.

==== code 60046: "file: <file name> - the parser is waiting for the reader for: <number> s (position: <number>, buffer: <number>-<number>, size: <number>, status: <number>, ret: <status>)" / "file: <file name> - the reader is waiting for free read buffer space for: <number> s (buffer: <number>-<number>, limit: <number>, size: <number>, status: <number>, ret: <status>)"

The reader and the parser of one redo log exchange data through the read buffer: the reader fills it, the
parser parses it and confirms (releases) the part it has consumed. One of the two waits here for the other one
for a longer time - either the parser waits for the reader to finish the archive (or to append more data), or
the reader waits for free space in the read buffer while the parser still holds it. The message reports the
read position, the current read buffer window (and its limit), the size of the redo log, the reader status and
its result code.

The warning is repeated while the condition persists (first after about 200 * `redo-read-sleep-us`, then every
1200 iterations). A single occurrence can be caused by a slow filesystem bridge, a repeating one means that
replication is stalled - the redo log mentioned in the message is the place to look at. Before this warning
existed such a stall produced no log message at all.

Since 2026-10-28 a repeated occurrence with the **reader side text only** (no matching "the parser is waiting
for the reader" line) is the signature of a handshake deadlock, not of a slow archive: the parser asked the
reader for a state change (warning 60067 reports it at the same time) and the reader can not answer because it
is parked in this very wait. Production 2026-10-27 and 2026-10-28 spent 6 and 9 hours in exactly that state.

==== code 60067: "the parser is waiting for the reader to serve: <checkRedoLog|updateRedoLog> for: <number> s - the reader is not serving it (status: <status>, buffer: <number>-<number>, limit: <number>, size: <number>, file: <file name>, reader thread: <context>/<reason>) ..." / "forcing the parser/reader handshake back to sleeping after: <number> s in: <...> (reset: <number> of 2, "handshake-timeout-us") ..."

The parser asked the reader to change state (`checkRedoLog`: open the archive again, `updateRedoLog`: re-read
its header and reset the window) and the reader did not serve the request within `handshake-timeout-us` (in the
`source` element, default 30 s, 0 = no bound). The two messages come in pairs: the first when the limit is
reached (at most once a minute while the wait lasts), the second when four times the limit is reached and the
handshake is **forced back to sleeping** - both condition variables are notified, so a reader parked anywhere
(including the "read buffer full" wait) is released and can serve the next request. The archive is opened again
and the saved position is kept, so nothing is lost; only when two forced resets do not help does the parser give
the archive back to the scheduler, which retries the open and reports 10009/10074 as usual.

The message carries what the attempt itself can not see: the reader status, its read window and limit, the size
of the file, the file name and the context/reason of the reader thread. Look there first: `status=SLEEPING` with
`reader thread: wait/READER_NO_WORK` means the reader never got the request, `status=READ` with a full window
means it is waiting for the parser to consume - the two ends of a handshake cycle.

This is the last line of defence behind warning 60055: it makes a stalled handshake visible after 30 s instead of
after hours, and it recovers without a restart.

==== code 60047: "no archived redo log was read for: <number> s, but <number> committed transaction(s) still wait for the low-water-mark (scn: <number>, thread watermarks: <text>, archives in the list: <number>, skipped: <number>, parked: <number>)"

Reported in archives-only mode when a pass over the archive list did not read anything while committed
transactions are still buffered in the commit sorter **and the first of them is already at or below the
low-water-mark**. The sorter is flushed only by the parser (the low-water-mark is the minimum parsed SCN over
the redo threads), so once the parser stops reading nothing can release those transactions any more: replication
stops delivering while the process looks exactly like an idle one. Transactions that wait *above* the
low-water-mark are the normal case (the other redo thread has not been parsed that far yet) and are not
reported. The message reports how long this has been going on, the SCN of the first buffered event and the
current low-water-mark, the per thread watermarks (a thread released by `idle-thread-release-us` or closed by
instance recovery is marked as such), how many archives are still in the list, how many were dropped as already
parsed and how many are parked waiting for a missing predecessor.

==== code 60055: "the parser made no progress for: <number> s (thread: <number>, file offset: <number>, pending commits: <number>) - locks held right now: <deliveryMtx|swapMtx|mtxTransaction|none of the probed ones>, delivery: <idle|in flight for: <number> s>, swap chunk waits: <number> (<number> ms)"

Only reported when the parser progress watchdog is enabled (`watchdog-us` in the `source` element, or the
environment variable `OLR_WATCHDOG` in seconds - it wins). It is meant to be switched on when a run has to be
diagnosed; with the default (off) it does not cost more than a predictable branch per redo block.

Since 2026-10-28 the line ends with `reader: status=... buffer=...-... size=... waiting=... s file=...`, a
snapshot the reader thread publishes on every state change and on every tick of its buffer-full wait. It names
whom the parser waits for - read it before the `layers:` fields: a parser stuck in a handshake (60067) shows
`status=SLEEPING` and a reader thread in `wait/READER_NO_WORK`, one waiting for the reader to consume shows
`status=READ` with `buffer` exactly `limit` apart.

_Progress is a position, not a call_: the parser publishes its position once per redo block, and until 2026-10-20
every one of those calls refreshed the watchdog timer. A parser that walked in circles over the same blocks
therefore looked exactly like a healthy one - production ran 26 minutes inside one archive (thread 2, seq 959664,
delivery frozen behind it) and this warning never fired. The timer is now refreshed only when the position
actually changes (redo thread, file offset or the number of commits waiting for delivery), so a parser that
stands still is reported `watchdog-us` after it stopped moving, and the message names the position it stands on.
Expect a handful of `no progress for: 0 s` reports around a healthy flush (the default `watchdog-us: 300000` is
shorter than one transaction flush): raise it to `2000000` if that is noise for the run.

The parser did not advance for the configured time. The message carries the last position it was seen at (redo
thread, file offset, commits waiting for delivery) and the result of a `try_lock` probe of the three locks that
can hold it without a trace line of their own: `deliveryMtx` (a delivery is in flight, `CommitSorter::flushReady`),
`mtxTransaction` (the schema/transaction mutex, held for a whole transaction flush) and `swapMtx` (the swap
memory of the transactions). The probe is read only and released immediately; nothing about the call order
changes.

Since the delivery runs on a thread of its own (the `DeliveryExecutor` thread - the parser publishes its
water-mark and enqueues, it does not deliver any more), a held `deliveryMtx` is *not* a sign of a stall: the gate
covers a whole delivery and the delivery thread holds it while it builds. The two extra fields say what the
delivery is doing (`delivery: in flight for: <number> s`, or `idle`) and how much of the time went into reading
transactions back from the swap file (`swap chunk waits`, the silent wait of `Ctx::swappedMemoryGet`; a single one
of them long enough to matter is reported by 60061).

A parser waiting for the next archive of a thread is expected and is reported by 60056 instead - the watchdog
stays quiet for it (it is suppressed while the archive list has nothing to hand out). The warning repeats with a
doubling interval (capped at eight times the threshold).

==== code 60056: "no archived redo log to read for: <number> s - the archive list source reports thread <number>: expected seq <number>, highest known seq <number>; ... (\"arch-wait-warn-us\")"

Reported in archives-only mode when the archive list source (for example `V$ARCHIVED_LOG` on the standby) hands
out no row for the sequence a redo thread needs, for longer than `arch-wait-warn-us` (microseconds, 1000000
default, `source` element). It names, per redo thread, the sequence that thread needs and the highest sequence
the source itself knows - so a source that is complete but does not advance (standby stopped applying, archive
destination full, `MRP` stuck) is told apart from one that is behind. Repeated with a doubling interval; an INFO
line is written when the sequence arrives ("... arrived after <number> s").

Before this warning existed both cases were silent: only a `TRACE` line with the archive list was written, which
is not enabled in production runs.

==== code 60057: "the swap entry of transaction: <xid> (thread: <number>, conId: <number>) is already gone during \"<stage>\" (the same Xid was parsed a second time and took the key over, or the delayed cleanup of the previous owner ran first) - the swapped out data of that transaction is not available any more, the parse continues without it"

The swap memory entry of a transaction that the parser (or the delivery) is working on has disappeared. That
happens when the same Xid is parsed a second time and takes the swap key over, or when the delayed cleanup of the
previous owner runs first. The entry carries the swapped out data of one transaction; once it is gone the answer
to "read it back" is "there is none", so `swappedMemorySize` returns 0, `swappedMemoryGet` and
`swappedMemoryShrink` return a null chunk and `swappedMemoryRelease` returns without doing anything - the parse
goes on and the delivery order and content of every other transaction are untouched (the entry was gone before
anything of this transaction was written out).

This used to be a fatal error (50070) and stopped the whole replicator, in the reproduction rig within seconds of
the situation appearing. Each event is counted in the `swap_entry_missing` counter of the `parse statistics`
line, so a run tells "it never happened" apart from "it happened and was survived".

==== code 60058: "the saved position of this pass (block <number>) is not the head of an lwn record in: <file> - the pass restarts at the beginning of this archive (the records of the transactions that were already delivered are dropped, the open ones are read again)"

With archive slicing on (`slice-pending-commits`), a pass saves the position it has to continue from and the next
pass of that archive starts there. The saved position is meant to be the head of the next LWN record, but that is
not a guarantee: it can be stale (the archive was already resumed and the position was consumed) or it can point
at a block that is not an LWN head at all. Instead of ending the run - error 50051 did exactly that, measured in
production: "invalid lwn scn: 11388144845283" right after "FINISHED (sliced), position: 7340032 / 13839360" - the
pass restarts at the first block of the archive. The records of the transactions that were already delivered are
dropped by the tombstone (`committed_reread_drops`), the transactions that are still open are read again, and the
archive is read once more: a cost, not a fault.

Counted in the `resume_fallbacks` counter of the `parse statistics` line. A delivery with slicing on should show
zero here - anything above zero means the saved positions are not usable and the archive is being read again.

==== code 60059: "transaction <xid> (thread: <number>) is parsed again while it is still open - the records parsed before are kept and the transaction is continued (a slice boundary or a restarted archive cut it)"

The undo slot of a transaction that has no commit yet is taken over by the same Xid: the redo of that transaction is
being read a second time. That happens when a slice boundary cut the transaction into two passes, or when a
restarted archive (60058) began before its commit. The transaction object keeps the records parsed before the cut
and the second read continues it, so the delivery of its commit sees the whole transaction - deleting the object
instead (which is what the slot-takeover path did, and still does for a *different* Xid, warning 60041) loses the
records parsed before the cut: measured on a sliced run, 120 rows less than the same archives without slicing,
exactly the heads of the transactions that straddled a boundary.

On the restart path the records of open transactions are read a second time and land in the same object again, so
the delivery is at-least-once for them - which is the documented contract (the consumer has to be idempotent). A
delivery with `slice-pending-commits: 0` should show zero of these: they only appear when archives are sliced or
restarted.

==== code 60060: "the stash of taken-over unfinished transactions is full (<number>) - the oldest (<xid>) is dropped, its rows are lost if its commit arrives later"

The side stash that keeps a transaction whose undo slot was taken over while it was open (see 60041/60059) has
reached its cap (1000 transactions). The oldest one is purged, and if its commit arrives later in the stream its
rows are lost - which is the behaviour the stash exists to prevent, so reaching the cap means the run is processing
far more concurrently open transactions than the cap assumes. Raise the cap (it is a compile time constant,
`TransactionBuffer::TAKEN_OVER_KEEP`) and report the run: a healthy delivery never comes near it.


At most one message per 30 seconds. A run that reports this has to be restarted (`pkill` +
restart): the scheduler resumes from the checkpoint and the saved file offsets, so the data is not lost, it is
only delayed.

==== code 60061: "still waiting after <number> s for the swapped out chunk <<number>> of transaction: <xid> (swap entries: <number>, swap entries waiting for their file to be removed: <number>, waits so far: <number>) - the memory manager brings one chunk back per iteration of its loop (\"swap-path\"), so a full or slow swap volume shows up as a stalled delivery (warning 60055 / 60062 name the caller)"

The delivery of a transaction that was swapped out reads its chunks back one by one
(`Ctx::swappedMemoryGet`), and the memory manager brings back one chunk per iteration of its loop, each with a
`stat`, an `open` (`O_DIRECT`), a `pread` and a `close` - plus one chunk written out per iteration
(`MemoryManager::run`). The delivery therefore runs at the rate of that pump, and until this warning existed
neither the wait nor the pump left any trace in the log: the production stall of 2026-10-15 (6 stalls in 7
minutes, up to 70 s, delivered at about 150 transactions/s while the healthy rate was 500-1300/s) reported
nothing but "locks held right now: deliveryMtx swapMtx" (60055), which reads like a lock problem.

Reported *while* the wait is still going on, every 30 seconds (the same interval as 60050 uses for
`Ctx::swappedMemoryInit`), not after it returned: a memory manager that never brings the chunk back (full swap
volume, an asmfs `stat` that hangs, the entry taken over by a re-parse) used to leave the caller inside the wait
with no line at all. The `waits so far` counter is the number of 30 s rounds, not of notify round trips, so a
climbing number with `still waiting` is a pump that is not moving. The totals of these waits are named by 60055
(`swap chunk waits`). A run that reports this has "swap-path" on a volume that can not keep up with the
transaction data rate: check that volume (a full
file system reports its own error, a slow one does not), `swap-mb`, `memory-max-mb` and the transaction rate.

==== code 60062: "the parser is waiting for the delivery for: <number> s - the commit sorter holds <number> chunk(s) of this thread against an allowance of <number> (of the <number> chunk(s) / <number> event(s) buffered in total, global cap: <number> chunk(s) of <number>, events of this thread: <number>, min share: <number>, deliverable now: <number>, above the low-water-mark: <number>, thread watermarks: <...>); the parse of this thread is stopped on purpose: ..."

The parser is stopped by the backpressure of the commit sorter for longer than 30 seconds: the sorter holds more
*chunks of the transaction pool* for this redo thread than its allowance allows. The allowance is not a fixed
share any more (`CommitSorter::allowanceLocked`): it is what is left of the global cap once the other redo threads
have what they already use plus their guaranteed minimum -

  allowance(t) = globalCap - (N-1)*minShare - sum(used(j), j != t)

with `globalCap` = half of the pool (`memory-max-mb` / `transaction-block-kb`; the other half must cover the open
transactions, the builder and the reader - that boundary is what keeps `10017` away) and `minShare` = an eighth of
the even split, at least `MIN_THREAD_CHUNKS`. A thread that has data therefore gets the pool that the quiet
threads are not using, while the sum over all threads stays below the cap. The measurement is chunks and not
events: a transaction can own many chunks, so a count of events against a chunk budget bounds nothing.

The wait is applied at the *head* of a redo record (`CommitSorter::waitForBacklog`, called from the parser right
after it published its water-mark there), not per commit: a record can carry more commits than the allowance
(measured: 4,097 commits in one record) and inside a record the water-mark only moves at the next head, so the
parser would wait for a water-mark only it could publish. The message names how much of the backlog the delivery
may take right now (`deliverable now`) and how much of it waits for a higher water-mark (`above the low-water-mark`),
plus the per thread water-marks with the threads that do not hold the water-mark marked `(closed)`, `(no work)` -
released because the archive list says they have nothing left to read, warning 60045 `reason: no-work` - or
`(released)` / `(unaligned)`.

The two numbers are what tells the two cases apart: a wait with a non-zero `deliverable now` is a delivery that
is behind on work it may take (check its side: 60061/60055 for the swap read back, 60031 for a full writer
queue, the pool size against the redo rate). A wait with `deliverable now: 0` would mean the water-mark is
holding the backlog back - that state used to be a deadlock (the parser is the only thread that publishes a
higher water-mark, so stopping it freezes the water-mark, the delivery stays idle and the backlog never drops:
measured in the reproduction rig on 2026-10-16 with slicing on, 60062 once and then 60055 eight times, the
delivery count frozen for 128 s). It is prevented at the source now: the parser publishes its water-mark at the
*head* of every record and not only at its end, so a wait that happens inside a record does not hold the
water-mark back at the previous one. A run that still reports `deliverable now: 0` here has a water-mark that is
pinned by something else - the thread watermarks in the message say which thread.

Why there is a bound at all: every buffered commit owns at least one chunk of the transaction pool, and a
transaction that owns a single chunk can not be swapped out (the swap pump needs more than one), so a backlog
larger than the pool can hold can not be relieved any more - the parser then blocks in `Ctx::getMemoryChunk`
and the run ends with `ERROR 10017 out of memory`. Until the delivery got a thread of its own the parser also
delivered inline, which bounded the backlog to one LWN window; with the delivery decoupled nothing paces the
parser, so it is paced here. Measured in the reproduction rig before this bound existed: 4,500 buffered commits
with a 4 GB pool and 1 MB blocks (4.5 GB) ended the run with 10017 while the same run on the previous code
delivered 18,625 commits with a backlog of 650.

A run that reports this keeps working - the wait ends as soon as the delivery drains the backlog (the lock is
released while waiting, and the low-water-mark moves as soon as the other redo threads publish, or as soon as a
thread that can not advance is released - 60045). It is reported once per wait, after 30 seconds. Seeing it
regularly means the delivery is systematically slower than the parse: check 60061/60055 (swap read back), the
writer's throughput (`60031`, `output queue is full`) and whether the pool is too small for the redo rate
(`memory-max-mb`, `transaction-block-kb`). A wait with `deliverable now: 0` and no `(no work)`/`(released)`
thread in the water-marks is the water-mark pinned by a thread that is *behind*, not released: that thread has to
be parsed further (its own allowance may be the reason it is not) before the backlog can move.

==== code 60063: "thread <number> is not rewound to its oldest unfinished transaction: seq: <number> (from \"min-trans\"/\"min-tran\") is <number> archive(s) behind the checkpoint position seq: <number>, over the limit of <number> (\"min-trans-rewind-max-archives\") - the redo before the checkpoint is NOT replayed, so a transaction of this thread that commits later is delivered with only the rows written after the restart (duplicates avoided, completeness given up for this thread)"

Only reported with `min-trans-rewind-max-archives` set (`source` element, 0 = no limit, the default). After a restart
the checkpoint carries, per redo thread, the position of the oldest unfinished transaction of that thread
(`min-trans`, written by `TransactionBuffer::checkpoint`). The thread is rewound to it, because a transaction whose
begin was before the restart can only be delivered completely if its redo is read again from the start - the parser
that resumes at the checkpoint position sees only its tail, and the commit then carries just those rows.

Re-reading that window has a price: every transaction that was already delivered from the same redo range is
delivered *again*, and the window is as long as the transaction was open (a transaction open for two hours on a
thread that archives 2.3 GB every two minutes is ~140 GB of redo and two hours of duplicates). This warning is the
counterweight: when the span (counted in archives of the thread's own sequence space - `threads[].seq` minus
`min-trans[].seq`) exceeds the configured limit, that thread keeps its checkpoint position and the transaction is
delivered **incomplete** instead. Both outcomes are deliberate; which one a run takes is visible in the log
(`rewinding thread N ... (from "min-trans")` versus this warning).

_IMPORTANT:_ when this is reported, the rows of that thread's unfinished transactions that were written before the
restart are **not** in the output. If they matter more than the duplicates, raise the limit (or set it to 0) and
restart again from a checkpoint that still carries the position; if the position is gone, the window can only be
replayed by resetting the checkpoint.

==== code 60064: "the parser is stopped by its commit credit for: <number> s - redo thread: <number> holds <number> buffered commit(s) against a credit of <number> ... - this is not a memory problem: the commits wait for a water-mark, so the parser of the thread that holds it (or its archive) is the one to look at"

Reported once per wait when a redo thread has been stopped at a record head by its commit credit
(`source` element, `pending-commits-per-thread`, default 4096, 0 = automatic) for longer than the backpressure
report interval. The credit is the bound on how far one redo thread may run ahead of the delivery; it is enforced in
`CommitSorter::waitForBacklog`, i.e. at a record boundary and not inside a record (a wait inside a record would wait
for a water-mark only the blocked parser could publish).

This warning is *not* about memory: it says the commits of this thread are buffered and waiting for the low-water-mark,
which is held by another redo thread. Look at the water-marks in the message (or at `backlog layers`) to see which
thread is behind, and at that thread's archives: still being written, missing, or read slowly. The chunk based
backpressure (`60062`) is the memory side of the same wait and is reported separately; a run that reports 60064 but
not 60062 has a *sequencing* problem, not a pool problem.

The credit holds a thread at its limit plus the commits of one record: a single record can carry more commits than the
credit (measured: 4,097 commits in one record against a limit of 4,096), and that overshoot is on purpose - waiting
inside the record would be the deadlock described above.

_IMPORTANT:_ with `pending-commits-per-thread` set to a very large value (or the versions before g4) this bound does not
exist; the backlog then grows until the pool is full and the swap pump takes over, which is what the production run of
2026-10-23 did (59,048 buffered commits, 18,245 swap entries, the parse falling to 1.6 MB/s).

==== code 60065: "swap chunks reached the limit: <number> of <number> chunk(s) are on the swap file - no further transaction is written out and the parser is stopped at a record boundary instead (the bound is a quarter of \"memory.max-mb\"); the delivery reading chunks back releases it"

Reported when the swap pump finds as many chunks written out as the bound allows (a quarter of the transaction pool,
derived from `memory.max-mb`; no per-machine setting). Nothing is written out past that point: the parser is stopped at
a record boundary instead (`CommitSorter::waitForBacklog`), so the pool drains through the delivery and not through the
disk. The condition clears itself as soon as the delivery has read chunks back - this is a bound, not a switch.

Why the bound exists: reading the transactions back competes with reading the archives (the same mount and the same
cores), so unbounded swapping turns a backlog into a slowdown of everything. Production 2026-10-23 reached 18,245 swap
entries and a parse at 0.3 MB/s (a 2.3 GB archive took 8,133 s instead of 11-15 s) with no warning at all.

_IMPORTANT:_ a run that reports this warning is *slower on purpose*. If it repeats, the cause is above this bound: the
delivery not keeping up (Kafka, the writer), a redo thread holding the low-water-mark, or a pool too small for the rows
the subscribed tables produce between two advances of the water-mark. It is reported at most once a minute.

==== code 60066: "the commit credit is lowered: <number> -> <number> commit(s) per redo thread - a parser was stopped by it for: <number> ms in the last report interval, delivery: <number>/s (\"pending-commits-per-thread\": 0 = automatic)"

Reported when the credit is in the automatic mode (`pending-commits-per-thread` = 0) and the delivery thread adapts it:
halved when a parser spent more than 5 s of the last 30 s report interval stopped by the credit (down to 512), raised by
a quarter when nothing was stopped by it and the buffered commits stay below a quarter of what it allows (back up to
4096). The same code reports the raise ("the commit credit is raised: ...").

The signal is deliberately *not* the delivery rate alone: a credit that stops the parsers means the design is working,
and the question the controller answers is only "how far ahead is useful on this machine". Each adjustment is a line in
the log, so the reason can be reconstructed afterwards - the value itself is also in `backlog layers` (`credit=`).

==== code 60067: "redo thread: <number> yielded archive seq: <number> <number> time(s) within a minute because it delivered no data for: <number> s - the parser is a single thread, so while it waits on this archive the other redo threads are not parsed either (check the archive itself: still being written, missing, or read slowly through the mount; \"stall-yield-us\")"

Reported on the fourth yield of the same redo thread within a minute. There is **one** parse thread: without this yield
an archive that delivers no data (still being written, missing from the mount, or read slowly) stops every other redo
thread for as long as it lasts. The parser saves its position at the last *confirmed* LWN boundary and returns, so the
scheduler parses another thread first and resumes this archive afterwards; resuming at a confirmed boundary re-reads at
most the redo of the record that had been started (counted like the STOPPED path, see `parse statistics`).

Tuning: `stall-yield-us` (`source` element, default 5000000 = 5 s, 0 = off). A yield costs a reopen of the archive, so
the threshold should stay well above the archive arrival jitter; the yield is rate limited per thread (twice the
threshold) and only happens when another archive is waiting to be parsed.

_IMPORTANT:_ repeated 60067 is a storage/archive-supply symptom, not a parser symptom: check whether that thread's
archives are complete when they are picked up (`thread_<n>_seq_<seq>` in the mount), and whether the mount is slow at
that moment. The yield keeps the other threads moving, it does not make this archive faster.

==== code 60068: "the builder output ring is full: <number> of <number> chunk(s) hold messages that the client has not confirmed - the delivery waits here, the commit sorter fills up and the parser is stopped by its credit (the bound is an eighth of \"memory.max-mb\"); confirming the messages releases it"

Reported at most once every 30 s while the builder output ring is at its bound. The ring holds the messages that have
been built (JSON) and handed to the writer but that the client has not confirmed yet; it grows by one pool chunk
(`transaction-block-kb`) per block of output and is now held at **an eighth of the pool**, i.e. of `memory.max-mb`.

Before this bound existed the ring was limited only by the pool itself, so a client that stopped reading let it eat
the whole pool while the commit sorter - the only place the parser's credit looks at - stayed empty. Measured on the
rig with a black-holed broker: 50,000 commits delivered, `sorter_pending=0`, `in_delivery=0`, `writer_queue` pinned at
21, and every message sitting in this ring. The state looked like "nothing is buffered" while 50 MB (in production:
up to 12 GB) were held.

What happens now: the delivery thread waits in `Builder::builderRotate()`, the events it had taken from the sorter stay
counted (`in_delivery`), the sorter fills up, and the credit stops the parser at a record head (`60064`). Memory is
bounded by the ring, the sorter and the swap bound together instead of by the pool alone.

What to do: this is a client-side stall, not a parser problem. Look at the writer (`60031` "failed to produce" /
`queue.full`), at the broker and at the consumer group. `builder_out` in `backlog layers` shows the occupancy, and
`60064` says whether the parser is waiting for the watermark, for the writer or for the client.
