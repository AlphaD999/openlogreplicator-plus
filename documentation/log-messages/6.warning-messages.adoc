==== code 60001: "incomplete row for table (obj: <number>), probably IOT, xid: <xid>, offset: <number>"

Occurs when a row cannot be reconstructed completely (common with IOTs or missing schema images).
Remediation: Ensure full schema mode or provide a schema snapshot; avoid schemaless mode for IOT tables.

==== code 60002: "unknown value (column: <column>): <number> - <data>)"

A column value could not be decoded (often seen with LOB fragments or unexpected formats).
Remediation: Enable detailed logging (`unknown=1`) to capture raw bytes and provide schema for proper decoding.

==== code 60029: "message size (<number>) will exceed 'max-file-size' size (<number>)"

A single generated message is larger than the writer's maximum file size.
Remediation: Increase `max-file-size` or use a writer without that limit.

==== code 60030: "rotation size is set too low (<number>), increase it, should rotate but too early (<file name>)"

Configured rotation threshold is too small and causes frequent rotations.
Remediation: Increase rotation size to reduce churn.

==== code 60031: "queue, full, sleeping <number> >ms, then retrying"

Writer queue is saturated; backpressure applied.
Remediation: Increase writer queue, improve sink throughput, or throttle source.

==== code 60032: "unknown request code: <message>"

Received an unsupported or unknown client request code.
Remediation: Verify client and server protocol versions for compatibility.

==== code 60033: "request decoder[<number>]: <data>"

Client request payload could not be decoded.
Remediation: Inspect client payload and ensure it follows the protocol.

==== code 60034: "observed UPDATE operation for NOT NULL column with NULL value for table <owner>.<table> column <column>"

Historical or partial data shows a NOT NULL column as NULL in BEFORE image.
Remediation: Usually harmless; set flag to copy AFTER into BEFORE if needed.

==== code 60035: "unknown database requested, got: <name>, expected: <name>"

Client requested a database not present in configuration.
Remediation: Client must request a configured database name.

==== code 60036: "incorrect XML data: <message>"

XMLTYPE column data could not be parsed or is malformed.
Remediation: Verify XML content and source XML dictionary metadata.

==== code 60037: "incorrect DDL data, offset: <number>"

DDL-related system data is malformed or unexpected.
Remediation: Inspect raw DDL records and source metadata; report if reproducible.

==== code 60038: "couldn't find archive log for thread: <number> seq: <number>, found: <number>, thread is closed - waiting for delayed archival (instance recovery), sleeping <number> us"

On a RAC source, the archive of a closed (stopped) instance's thread is missing while later sequences exist.
The tail archive may still be produced by instance recovery on a surviving node; OpenLogReplicator keeps waiting instead of failing.
Remediation: Verify instance recovery/archival on the remaining nodes; if the archive never appears, restore it manually (report this issue if it persists).

==== code 60039: "RAC database detected - archives-only mode can not be disabled, the reader parameter \"archives-only\": false is ignored"

A RAC source database always runs in archives-only mode, because online redo logs of a RAC database reside in ASM and are not readable from outside the cluster.
An explicit `"archives-only": false` in the reader configuration therefore has no effect on a RAC database.
Remediation: Remove the parameter to silence the warning; only a non-RAC database can use online mode.

==== code 60041: "transaction <xid> takes over the undo slot of unfinished <xid> - the unfinished transaction is dropped"

An undo slot holds one active transaction at a time. When OpenLogReplicator sees a different transaction
take over a slot it had seen as still open, the previous transaction is assumed to have committed or
rolled back unobserved (which is expected when reading starts in the middle of the redo stream).
The unfinished transaction is discarded to let processing continue.
Remediation: Only reported with the `RECOVER_BROKEN_TRANSACTION` flag (`1 << 19`). Usually harmless;
if reported frequently, start reading from a position with no transactions in flight.

==== code 60042: "duplicate <owner>.<table> value for unique (<columns>), dropped: <columns>"

The unique key of a dictionary row is already indexed by a different row. This happens when the same
object is present in more than one container of a CDB, or when the same redo stream is processed twice.
Remediation: Only reported with the `ADAPTIVE_SCHEMA` flag (`1 << 2`), in which case the newly read row
wins and the previous holder is discarded. Without the flag the same condition is an error (50024).

==== code 60043: "memory pool exhausted with nothing left to swap for <seconds> s (allocated: <number> MB of <number> MB, free: <number> MB, blocked: <number> thread(s), open transactions: <number>, swappable: <number>) - modules: <modules> - replication is likely stalled; increase \"max-mb\", verify \"swap-path\" is writable, or skip the big transaction via \"transaction-max-mb\""

The memory pool is completely allocated, at least one thread is waiting for a chunk and the memory manager
has no transaction chunk left to swap out, so the parser (waiting for transaction memory) and the reader
(waiting for a read buffer) can no longer make progress. The message reports the pool state, how many
threads are blocked, how many transactions are open, how many of them are swappable and the per module
memory usage. Replication is stalled until the condition resolves.

Two independent limits can lead here:
* a single transaction bigger than the configured `max-mb` (or `swap-path` does not exist or is not writable -
  in that case transactions cannot be swapped out at all; `swap-path` is validated at startup since this
  release);
* the number of concurrently open transactions: every open transaction occupies at least
  `MEMORY_CHUNK_SIZE_MB` and only transactions with more than one chunk are swappable, so a workload with
  thousands of concurrent transactions can exhaust the pool even with small transactions. This case is
  reported with `swappable: 0`. Note that a fresh start positioned in the middle of an archive re-reads the
  whole archive from its beginning, so the peak number of open transactions can be the whole pre-start
  part of an archive.

Remediation: increase `memory.max-mb` (at least 110% of the biggest expected transaction and at least the
peak number of concurrently open transactions in MB plus the read/write buffers), make sure
`memory.swap-path` exists and is writable by the process user, or set `transaction-max-mb` to skip
transactions bigger than the configured size (their data is not replicated).

When the parser itself is blocked and nothing can be swapped out, the run is not recoverable (the commit
sorter is flushed only by the parser) and OpenLogReplicator terminates with error 10017 instead of waiting
forever.

==== code 60044: "file: <file name> - position: <number> - short read before the end of file (size: <number>), the file is not fully readable yet"

An archived redo log could not be read up to the position the reader expects to have:
either the read returned zero bytes although the file is larger than the current position, or the position
did not move at all for a longer time ("no progress at position: ..., size: ... for: ... s").

A filesystem bridge can report a size the file does not have yet - asmfs, for example, snapshots the size of
an ASM file when it is opened and answers later reads with zero bytes when the file was not fully visible at
that moment. The reader does not treat this as the end of the archive (that would silently skip the rest of
it and move the checkpoint past redo that was never read): it stops and the archive is read again on the next
pass, which is why the same warning can repeat.

Remediation: check the filesystem bridge (mount options, `arch-read-tries`/`arch-read-sleep-us` retry window),
or use a destination where the archive is written before it is read.
Repeated short reads are usually harmless for the data - they only delay replication.

==== code 60045: "redo thread: <number> did not advance for: <number> s - it stops holding back the low-water-mark (\"idle-thread-release-us\"); its transactions can now be delivered after transactions with a higher SCN"

Only reported with `idle-thread-release-us` set (`source` element, 0 = disabled). The redo thread did not
report a new parsed SCN within the configured timeout, so it was left out of the low-water-mark of the commit
sorter. This bounds the memory that transactions of the other threads keep while an instance is idle.

_IMPORTANT:_ the global SCN order is not guaranteed for the transactions of the released thread any more - if
it later delivers redo with an SCN below what has already been written, those transactions are written after
transactions with a higher SCN. Remove the parameter (or set it to a higher value) if strict ordering by SCN
is required.

==== code 60046: "file: <file name> - the parser is waiting for the reader for: <number> s (position: <number>, buffer: <number>-<number>, size: <number>, status: <number>, ret: <status>)" / "file: <file name> - the reader is waiting for free read buffer space for: <number> s (buffer: <number>-<number>, limit: <number>, size: <number>, status: <number>, ret: <status>)"

The reader and the parser of one redo log exchange data through the read buffer: the reader fills it, the
parser parses it and confirms (releases) the part it has consumed. One of the two waits here for the other one
for a longer time - either the parser waits for the reader to finish the archive (or to append more data), or
the reader waits for free space in the read buffer while the parser still holds it. The message reports the
read position, the current read buffer window (and its limit), the size of the redo log, the reader status and
its result code.

The warning is repeated while the condition persists (first after about 200 * `redo-read-sleep-us`, then every
1200 iterations). A single occurrence can be caused by a slow filesystem bridge, a repeating one means that
replication is stalled - the redo log mentioned in the message is the place to look at. Before this warning
existed such a stall produced no log message at all.

==== code 60047: "no archived redo log was read for: <number> s, but <number> committed transaction(s) still wait for the low-water-mark (scn: <number>, thread watermarks: <text>, archives in the list: <number>, skipped: <number>, parked: <number>)"

Reported in archives-only mode when a pass over the archive list did not read anything while committed
transactions are still buffered in the commit sorter **and the first of them is already at or below the
low-water-mark**. The sorter is flushed only by the parser (the low-water-mark is the minimum parsed SCN over
the redo threads), so once the parser stops reading nothing can release those transactions any more: replication
stops delivering while the process looks exactly like an idle one. Transactions that wait *above* the
low-water-mark are the normal case (the other redo thread has not been parsed that far yet) and are not
reported. The message reports how long this has been going on, the SCN of the first buffered event and the
current low-water-mark, the per thread watermarks (a thread released by `idle-thread-release-us` or closed by
instance recovery is marked as such), how many archives are still in the list, how many were dropped as already
parsed and how many are parked waiting for a missing predecessor.

==== code 60055: "the parser made no progress for: <number> s (thread: <number>, file offset: <number>, pending commits: <number>) - locks held right now: <deliveryMtx|swapMtx|mtxTransaction|none of the probed ones>"

Only reported when the parser progress watchdog is enabled (`watchdog-us` in the `source` element, or the
environment variable `OLR_WATCHDOG` in seconds - it wins). It is meant to be switched on when a run has to be
diagnosed; with the default (off) it does not cost more than a predictable branch per redo block.

The parser did not advance for the configured time. The message carries the last position it was seen at (redo
thread, file offset, commits waiting for delivery) and the result of a `try_lock` probe of the three locks that
can hold it without a trace line of their own: `deliveryMtx` (a delivery is in flight, `CommitSorter::flushReady`),
`mtxTransaction` (the schema/transaction mutex, held for a whole transaction flush) and `swapMtx` (the swap
memory of the transactions). The probe is read only and released immediately; nothing about the call order
changes.

A parser waiting for the next archive of a thread is expected and is reported by 60056 instead - the watchdog
stays quiet for it. The warning repeats with a doubling interval (capped at eight times the threshold).

==== code 60056: "no archived redo log to read for: <number> s - the archive list source reports thread <number>: expected seq <number>, highest known seq <number>; ... (\"arch-wait-warn-us\")"

Reported in archives-only mode when the archive list source (for example `V$ARCHIVED_LOG` on the standby) hands
out no row for the sequence a redo thread needs, for longer than `arch-wait-warn-us` (microseconds, 1000000
default, `source` element). It names, per redo thread, the sequence that thread needs and the highest sequence
the source itself knows - so a source that is complete but does not advance (standby stopped applying, archive
destination full, `MRP` stuck) is told apart from one that is behind. Repeated with a doubling interval; an INFO
line is written when the sequence arrives ("... arrived after <number> s").

Before this warning existed both cases were silent: only a `TRACE` line with the archive list was written, which
is not enabled in production runs.

==== code 60057: "the swap entry of transaction: <xid> (thread: <number>, conId: <number>) is already gone during \"<stage>\" (the same Xid was parsed a second time and took the key over, or the delayed cleanup of the previous owner ran first) - the swapped out data of that transaction is not available any more, the parse continues without it"

The swap memory entry of a transaction that the parser (or the delivery) is working on has disappeared. That
happens when the same Xid is parsed a second time and takes the swap key over, or when the delayed cleanup of the
previous owner runs first. The entry carries the swapped out data of one transaction; once it is gone the answer
to "read it back" is "there is none", so `swappedMemorySize` returns 0, `swappedMemoryGet` and
`swappedMemoryShrink` return a null chunk and `swappedMemoryRelease` returns without doing anything - the parse
goes on and the delivery order and content of every other transaction are untouched (the entry was gone before
anything of this transaction was written out).

This used to be a fatal error (50070) and stopped the whole replicator, in the reproduction rig within seconds of
the situation appearing. Each event is counted in the `swap_entry_missing` counter of the `parse statistics`
line, so a run tells "it never happened" apart from "it happened and was survived".

==== code 60058: "the saved position of this pass (block <number>) is not the head of an lwn record in: <file> - the pass restarts at the beginning of this archive (the records of the transactions that were already delivered are dropped, the open ones are read again)"

With archive slicing on (`slice-pending-commits`), a pass saves the position it has to continue from and the next
pass of that archive starts there. The saved position is meant to be the head of the next LWN record, but that is
not a guarantee: it can be stale (the archive was already resumed and the position was consumed) or it can point
at a block that is not an LWN head at all. Instead of ending the run - error 50051 did exactly that, measured in
production: "invalid lwn scn: 11388144845283" right after "FINISHED (sliced), position: 7340032 / 13839360" - the
pass restarts at the first block of the archive. The records of the transactions that were already delivered are
dropped by the tombstone (`committed_reread_drops`), the transactions that are still open are read again, and the
archive is read once more: a cost, not a fault.

Counted in the `resume_fallbacks` counter of the `parse statistics` line. A delivery with slicing on should show
zero here - anything above zero means the saved positions are not usable and the archive is being read again.

==== code 60059: "transaction <xid> (thread: <number>) is parsed again while it is still open - the records parsed before are kept and the transaction is continued (a slice boundary or a restarted archive cut it)"

The undo slot of a transaction that has no commit yet is taken over by the same Xid: the redo of that transaction is
being read a second time. That happens when a slice boundary cut the transaction into two passes, or when a
restarted archive (60058) began before its commit. The transaction object keeps the records parsed before the cut
and the second read continues it, so the delivery of its commit sees the whole transaction - deleting the object
instead (which is what the slot-takeover path did, and still does for a *different* Xid, warning 60041) loses the
records parsed before the cut: measured on a sliced run, 120 rows less than the same archives without slicing,
exactly the heads of the transactions that straddled a boundary.

On the restart path the records of open transactions are read a second time and land in the same object again, so
the delivery is at-least-once for them - which is the documented contract (the consumer has to be idempotent). A
delivery with `slice-pending-commits: 0` should show zero of these: they only appear when archives are sliced or
restarted.

==== code 60060: "the stash of taken-over unfinished transactions is full (<number>) - the oldest (<xid>) is dropped, its rows are lost if its commit arrives later"

The side stash that keeps a transaction whose undo slot was taken over while it was open (see 60041/60059) has
reached its cap (1000 transactions). The oldest one is purged, and if its commit arrives later in the stream its
rows are lost - which is the behaviour the stash exists to prevent, so reaching the cap means the run is processing
far more concurrently open transactions than the cap assumes. Raise the cap (it is a compile time constant,
`TransactionBuffer::TAKEN_OVER_KEEP`) and report the run: a healthy delivery never comes near it.


At most one message per 30 seconds. A run that reports this has to be restarted (`pkill` +
restart): the scheduler resumes from the checkpoint and the saved file offsets, so the data is not lost, it is
only delayed.
